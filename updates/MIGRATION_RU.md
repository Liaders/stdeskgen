# Перенос CortenDesk и StatusDesk

Эта пара скриптов рассчитана на нашу установку: контейнер `cortendesk`, SQLite,
Apache и домен `desk.status16.ru`, каталог загрузок `/srv/stdesk-updates`.
Резервные копии содержат секреты. Не публикуйте их в GitHub, на сайте или в чате.

## Старый сервер

Запустите `sudo bash backup-cortendesk.sh`. Контейнер временно останавливается
для согласованной копии, затем запускается обратно. Сжатие и сохранение образа
выполняются уже при работающем контейнере. Понадобится свободное место для
несжатой копии, Docker-образа и итогового архива. Скачайте `.tar.gz` и `.sha256`.
Если обнаружена внешняя БД, скрипт останавливается до остановки контейнера.

## Новый сервер

Нужна отдельная Ubuntu 24.04+ с установленными Python 3.12+, Docker и Apache.
Скрипт не устанавливает пакеты и не скачивает образ контейнера. Старый публичный
IP, существующий контейнер `cortendesk`, существующий сайт/каталог обновлений
или сертификаты — причина остановиться и выполнить перенос вручную.

Передайте `restore-cortendesk.py`, архив и его `.sha256` на новый сервер,
например в `/home/ubuntu/`. Имена архива и checksum должны совпадать, кроме
добавленного суффикса `.sha256`.

Только подготовка (создаёт остановленный контейнер, раскладывает данные,
копирует конфигурацию сайта и включает необходимые модули, но не активирует сайт):

```bash
sudo python3 /home/ubuntu/restore-cortendesk.py /home/ubuntu/cortendesk-migration-ДАТА.tar.gz
```

Полное восстановление с запуском — выберите его СРАЗУ вместо предыдущей команды:

```bash
sudo python3 /home/ubuntu/restore-cortendesk.py /home/ubuntu/cortendesk-migration-ДАТА.tar.gz --activate
```

После подготовки без `--activate` повторный запуск скрипта не допускается,
поскольку контейнер уже существует. Для активации используйте команды,
которые скрипт вывел в конце. После неудачи данные не удаляются автоматически;
не запускайте скрипт повторно, пока не изучена причина.

Тома переносятся в приватный `/srv/cortendesk-restore-*/data`, контейнер создаётся
с исходными переменными окружения, точным образом и привязками портов.
Каталог `/var/lib/docker` целиком не восстанавливается. Старая сеть Docker
заменяется стандартной bridge: внешних контейнеров-зависимостей быть не должно.
Привилегированные контейнеры, специальные устройства, host network и явные
привязки к старому IP требуют ручной адаптации. Состояние пользователей,
псевдонимы, ключи ID/relay и APP_KEY сохраняются из данных и конфигурации.

Apache: копируется только наш VirtualHost и сертификаты, а не весь старый
глобальный конфиг. Исходные файлы доступны под `host-reference` для проверки.
Если в VirtualHost есть дополнительные Include или нестандартные модули,
`configtest` остановит активацию; их следует перенести отдельно. Старые cron,
compose и сетевые конфиги автоматически не включаются.

## Проверка и переключение

Проверьте новый сервер до смены DNS, заменив НОВЫЙ_IP на его адрес:

```bash
curl --resolve desk.status16.ru:443:НОВЫЙ_IP https://desk.status16.ru/api/version
curl --resolve desk.status16.ru:443:НОВЫЙ_IP https://desk.status16.ru/client/channels/statusdesk/stable/windows-x64.json
```

Разрешите в облачной группе безопасности нужные порты. Затем измените A-запись
`desk.status16.ru` на новый IP. Сетевые настройки старого облака НЕ переносите.
Настройте продление сертификатов certbot и SSH/права публикации на новом хосте
отдельно: системные пользователи и SSH-доступ этим архивом не восстанавливаются.

После успешной проверки переключите клиентов и остановите старый контейнер.
Не оставляйте две независимые копии базы работающими надолго: они разойдутся.
Изменения после момента резервной копии в неё не входят. Для окончательного
переноса желательно сделать свежую копию при согласованной остановке записей.

Автоматическая проверка скрипта охватывает checksum, защиту распаковки и
сохранение параметров контейнера. Полное развёртывание на отдельной Linux ВМ
пока не проверялось.
