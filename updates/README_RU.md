# Канал обновлений StatusDesk

Адрес: **https://desk.status16.ru/client**. Apache2 раздаёт статические файлы
в обход приложения CortenDesk. Изменять код или базу CortenDesk не нужно.
Здесь нет загружаемого из интернета PHP-скрипта и HTTP API для публикации.

## Что реализовано

- Отдельный, включаемый при сборке механизм для установленного Windows x64
  клиента RustDesk 1.5.0; без конфигурации исходный путь не меняется.
- Подписанное Ed25519 описание выпуска, проверка продукта, канала, имени
  приложения, архитектуры, срока действия, возрастающей ревизии, размера и
  SHA-256 EXE. Перенаправления HTTP запрещены; адреса файлов строятся только
  внутри настроенного HTTPS-пути. Старые штатные проверки обновлений для
  этой сборки отключаются, чтобы клиент не получил оригинальный RustDesk.
- Повторное использование штатного установщика `--update`, без удаления
  настроек, ID, псевдонимов или конфигурационных каталогов.
- Проверка отсутствия активных сеансов до скачивания и до установки.
- Поддержка стратегий `allow-auto-update` CortenDesk. Этот параметр должен
  быть включён на целевом устройстве; сам сервер не публикует обновления.
- Подпись выполняется только локально: ключ зашифрован Windows DPAPI и не
  передаётся в GitHub или на сервер. В GitHub уходит проверенный подписанный ZIP.
- Workflow **Publish StatusDesk update** проверяет уже готовый пакет публичным
  ключом из Repository Variable `STDESK_UPDATE_PUBLIC_KEY`. Подпись в Actions
  не создаётся. Пакет хранится как вложение черновика GitHub Release.
- Публикация отдельно от компиляции: сначала локальная команда `prepare`,
  затем отдельная `publish`. Без `--deploy` пакет только проверяется в Actions;
  с `--deploy` передаётся на сервер по SSH после настройки его доступа.
- Сначала неизменяемый каталог выпуска, затем атомарная смена файла канала.
  Параллельная публикация блокируется. Существующие выпуски не перезаписываются.

## Первое подключение

Уже выданные клиенты не знают этот канал. Нужна **одна ручная установка**
первой сборки с адресом и публичным ключом. Она не может сама «узнать» новый
адрес из факта загрузки файла в CortenDesk.

В корне рабочего каталога на Windows:

```powershell
rdgen\.venv\Scripts\python.exe rdgen\updates\local_release.py init
```

Команда создаёт `.local-update-keys/signing-key.dpapi` внутри rdgen и печатает
только публичный ключ. Папка исключена из Git. DPAPI привязывает расшифровку
к текущему профилю Windows; копия файла сама по себе не является переносимой
резервной копией. Программа, уже работающая с правами этого пользователя,
может вызвать DPAPI — от заражённого компьютера такая защита не спасает.

Создайте переносимую резервную копию с отдельным паролем и храните вне репозитория:

```powershell
rdgen\.venv\Scripts\python.exe rdgen\updates\local_release.py backup --output "$env:USERPROFILE\Documents\StatusDesk-signing-backup.enc"
```

Пароль вводится в локальном терминале, в чат или GitHub не передаётся.
Копия зашифрована SecretBox; ключ выводится через Argon2id с отдельной солью.
Восстановление на другом Windows-компьютере, где ещё нет ключа:

```powershell
rdgen\.venv\Scripts\python.exe rdgen\updates\local_release.py restore --backup "путь\StatusDesk-signing-backup.enc"
```

В конструкторе используйте содержимое `updates/statusdesk-test.example.json`.
Это публичная конфигурация с адресом, публичным ключом, продуктом, каналом и
ревизией. Закрытый ключ и пароль резервной копии в конфигурацию не попадают.

В следующей сборке оставьте тот же ключ, продукт, канал, имя приложения и
настройки; увеличьте `revision` до 2. Ревизия независима от версии исходного
RustDesk: можно выпустить новые наши изменения на той же основе 1.5.0.
Канал `test` и канал `stable` — отдельные серии сборок. Клиент не переключается
между ними сам. Смена канала/ключа пока требует ручной переустановки.
Для возврата к предыдущему коду соберите его с новой, большей ревизией.

Настройку `allow-auto-update` включите в клиенте или стратегии CortenDesk.
Проверка начинается через штатные 30 секунд запуска сервиса, далее примерно
раз в сутки; при занятых сеансах/ошибках повторяется позже. Это не немедленная
команда «обновить все» из консоли. Часы компьютеров должны быть корректными.
Срок действия подписанного описания — год: даже без новых изменений нужно
вовремя выпускать новую ревизию. Истёкшее описание не устанавливается.

## Apache2: подготовка на сервере

Для предоставленного пользователем VirtualHost подготовлен полный файл
`desk.status16.ru.conf`. В нём добавлены исключения `/client/` для HTTP и
WebSocket-прокси, статический Alias и исключение файлов обновлений из
подмены названий. Сертификаты, адрес CortenDesk, WebSocket-маршруты и правила
брендинга остальных страниц сохранены. Файл следует перенести на сервер,
сохранить резервную копию действующего конфига, выполнить `apache2ctl configtest`
и только при `Syntax OK` перезагрузить Apache командой `systemctl reload apache2`.
Папка `/srv/stdesk-updates/public` должна существовать до проверки.

Нужен доступ администратора к серверу и HTTPS VirtualHost `desk.status16.ru`.
Перед применением следует проверить действующий VirtualHost: настройки ниже
не заменяют его и не меняют прокси CortenDesk.

Создайте отдельного пользователя `stdesk-update` с доступом по выделенному
SSH-ключу. От имени root подготовьте:

```bash
install -d -m 755 /srv/stdesk-updates /srv/stdesk-updates/bin
install -d -o stdesk-update -g stdesk-update -m 755 /srv/stdesk-updates/public
install -d -o stdesk-update -g stdesk-update -m 700 /srv/stdesk-updates/incoming
```

В `/srv/stdesk-updates/bin/` скопируйте `deploy.py`, `release.py`, `config.py`.
Владелец скриптов — root, без права записи пользователю публикации.
Установите Python 3.11+ и PyNaCl (например пакет дистрибутива `python3-nacl`).
В `/srv/stdesk-updates/public-key.hex` запишите **только публичный** ключ;
владелец root, режим 644. Публичный каталог Apache должен быть доступен только
для чтения пользователю веб-сервера.

Вставьте содержимое `apache-client.conf` **внутрь HTTPS VirtualHost**.
Если используется `ProxyPass / ...`, исключение `ProxyPassMatch "^/client(?:/|$)" "!"` должно
стоять раньше него. Если фронтенд настроен через RewriteRule с флагом `[P]`,
ему тоже понадобится исключение `/client/` до общего правила. Точное место
зависит от текущей конфигурации Apache. Проверьте `apache2ctl configtest`
и только после успешной проверки перезагрузите конфигурацию Apache.
Отсутствующий выпуск должен давать HTTP 404 из каталога, а не страницу входа
или HTML-ответ Laravel. Проверьте, что `/login` и `/api/peers` CortenDesk
по-прежнему работают.

Документация Apache:
[Alias](https://httpd.apache.org/docs/2.4/mod/mod_alias.html#alias),
[исключения ProxyPass](https://httpd.apache.org/docs/2.4/mod/mod_proxy.html#proxypass).

## Публикация

Закрытого ключа подписи в GitHub Secrets **нет**. Старый параметр
`STDESK_UPDATE_SIGNING_SEED` больше не используется и не требуется.

После проверки сборки подготовьте её локально (замените 123 номером run):

```powershell
rdgen\.venv\Scripts\python.exe rdgen\updates\local_release.py prepare --run-id 123 --output rdgen\.local-update-bundles\revision-2
```

Скачивается только успешная сборка Windows x64 из master с build receipt.
Команда сверяет ключ, подписывает описание и сохраняет пакет локально.
Для этого нужен доступ к GitHub через уже настроенный Git Credential Manager.
Отдельно отправьте проверенный результат:

```powershell
rdgen\.venv\Scripts\python.exe rdgen\updates\local_release.py publish --bundle rdgen\.local-update-bundles\revision-2 --deploy
```

В GitHub загружается ZIP с четырьмя разрешёнными публичными файлами: EXE,
описание выпуска, описание канала и provenance. Добавленные файлы, включая
случайно скопированные ключи, отклоняются. До отправки проверяются подпись
и хеш EXE. Во время `publish` закрытый ключ даже не открывается: используется
только сохранённый публичный ключ. Создаётся черновик GitHub Release и
запускается workflow проверки/публикации. При ошибке пакет остаётся в черновике
для диагностики; автоматической публикации GitHub Release нет.

Команда сама настраивает **публичную** Repository Variable
`STDESK_UPDATE_PUBLIC_KEY`; другое существующее значение не перезаписывается.
Для доставки на сервер нужны только SSH-секреты (подпись в них не хранится):

- `STDESK_UPDATE_HOST`: SSH-адрес сервера (хост или IP; не URL).
- `STDESK_UPDATE_USER`: отдельный пользователь `stdesk-update`, без sudo.
- `STDESK_UPDATE_SSH_KEY`: выделенный закрытый SSH-ключ публикации.
- `STDESK_UPDATE_KNOWN_HOSTS`: проверенная строка публичного ключа SSH-сервера.

SSH-доступ ещё требует отдельной настройки. Не добавляйте туда личный ключ
администратора сервера. Можно пока убрать `--deploy`: проверка пакета в GitHub
пройдёт без доступа к серверу и без изменения доступного клиентам канала.

Без SSH можно скачать пакет, перенести каталог bundle на сервер и запустить:

```bash
python3 /srv/stdesk-updates/bin/deploy.py \
  --bundle /путь/к/bundle \
  --root /srv/stdesk-updates/public \
  --public-key-file /srv/stdesk-updates/public-key.hex
```

Открытый адрес канала:
`https://desk.status16.ru/client/channels/statusdesk/test/windows-x64.json`.
Старые каталоги выпусков следует хранить для диагностики. Каталоги входящих
пакетов можно удалять после успешной публикации.

## Проверка перед основным каналом

1. Установить ревизию 1 в отдельную Windows x64 VM, включить автообновление.
2. Задать ID/пароль, авторизацию и локальный псевдоним; записать значения.
3. Собрать ревизию 2 того же приложения и test-канала с видимым изменением.
4. Проверить её вручную, затем опубликовать именно этот успешный run.
5. Дождаться проверки, подтвердить замену программы и сохранность настроек.
6. Проверить неверную подпись/повреждённый файл и активный сеанс: установка
   не должна происходить. Повторно убедиться, что CortenDesk работает.

## Ограничения и поверхность изменений

На сервер и устройства пока ничего не устанавливается этими файлами.
Реальное обновление требует развернуть каталог Apache и провести VM-проверку.
Windows x86, MSI-установки, portable, Linux и macOS пока не подключены.
Для MSI или клиента «Только исходящие» этот канал пока использовать не нужно.
Сохранение всех настроек после настоящего обновления требует практической
проверки, хотя код использует существующий путь установки без очистки профиля.
Подпись канала Ed25519 не является Authenticode-подписью Windows EXE.

Адаптер меняет только `src/updater.rs` (тонкий вызов отдельного модуля и
кавычки пути установщика), добавляет `src/rdgen_update.rs` и отключает штатную
проверку в `src/common.rs` для сборки с собственным каналом. Код установки и
каталоги настроек не переписываются. В генераторе добавлены валидация,
необязательное поле, передача конфигурации и отдельная публикация. Старые
сборки без конфигурации продолжают использовать прежние исходники.
