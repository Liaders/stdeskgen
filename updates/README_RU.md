# Канал обновлений StatusDesk

Для единого окна с вкладками «Конструктор» и «Публикация» запускайте
`start-desktop.cmd`. Полная инструкция: [DESKTOP_RU.md](../DESKTOP_RU.md).

Адрес: **https://desk.status16.ru/client**. Apache2 раздаёт файлы отдельно
от CortenDesk. Собственные ключи подписи, DPAPI, пароли резервных копий и
локальная подпись удалены по решению пользователя. Ключи подключения к
серверу RustDesk и проверка HTTPS-сертификатов остаются прежними.

## Страница скачивания для пользователей

### Самостоятельная публикация с Windows

1. В GitHub Actions откройте нужную **успешную** сборку. В Artifacts скачайте
   архив для требуемой платформы, распакуйте и проверьте установщик.
2. Откройте PowerShell в корневой папке проекта (той, внутри которой rdgen).
3. Выполните, указав свой путь к файлу:

```powershell
rdgen\.venv\Scripts\python.exe rdgen\updates\publish_from_windows.py --file "C:\путь\StatusDesk.exe" --platform windows-x64 --version 1.5.0
```

Адрес сервера, SSH-порт, пользователь и путь к локальному PuTTY-ключу заданы
в `rdgen/.local-publish.json` на этом компьютере. Файл исключён из Git и не
содержит самого ключа. На другом компьютере потребуется собственный такой
файл с полями host, port, user, key_file. Установлены должны быть Python из
venv проекта и PuTTY с plink/pscp. Сервер должен быть доступен по сети;
используется проверенный PuTTY host key, автоматического принятия чужого нет.
У пользователя Ubuntu нужны уже настроенные права `sudo -n` для публикации.

Команда проверяет формат и разрядность Windows EXE, загружает файл, сверяет
SHA-256 и запускает серверный скрипт публикации. Закрытый SSH-ключ остаётся
локальным. Затем обновите страницу /client/ — кнопка появится автоматически.
Повторная публикация той же платформы заменяет её ссылку в каталоге;
остальные платформы сохраняются. Старые файлы остаются на сервере.

| Дистрибутив | Значение --platform |
|---|---|
| Windows 64 бита, EXE | windows-x64 |
| Windows 32 бита, EXE | windows-x86 |
| Linux Intel/AMD, DEB/AppImage | linux-x64 |
| Linux ARM64, DEB/AppImage | linux-arm64 |
| macOS Intel, DMG | macos-x64 |
| macOS Apple Silicon, DMG | macos-arm64 |
| Android APK | android-arm64 / android-armv7 / android-x64 |

Эта команда публикует файл для скачивания и **не включает автообновление**.
Номер --version отображается на странице. Не публикуйте промежуточный,
непроверенный файл или EXE с чужими серверными настройками.

Файл `index.html` нужно разместить в `/srv/stdesk-updates/public/index.html`.
На странице есть Windows 64/32 бита, Linux x64/ARM64 и macOS Intel/Apple Silicon.
Кнопки появляются только для записей в `downloads.json`; без опубликованных
дистрибутивов отображается «Пока недоступно». Список каталогов остаётся закрытым.
При публикации stable-обновления Windows x64 каталог пополняется автоматически;
test-выпуски не заменяют пользовательскую загрузку.

Готовые дистрибутивы других платформ можно независимо добавить на страницу,
не включая их в автообновление. Перенесите файл на сервер, затем выполните:

```bash
python3 /srv/stdesk-updates/bin/publish_download.py \
  --root /srv/stdesk-updates/public \
  --file /путь/StatusDesk.exe --platform windows-x86 --version 1.5.0
```

Нужны скрипты `publish_download.py` и `download_catalog.py` рядом с deploy.py.
Платформы: windows-x64, windows-x86, linux-x64, linux-arm64, macos-x64, macos-arm64.
Файл копируется до обновления каталога, прежние платформы сохраняются.
Для Windows принимается EXE, Linux — DEB/AppImage, macOS — DMG.
Расширение не подтверждает правильность сборки: публиковать следует проверенные
дистрибутивы нужной архитектуры и настроек организации.

## Как работает обновление

1. Конструктор отправляет сборку в GitHub Actions.
2. После проверки EXE оператор отдельно запускает **Publish StatusDesk update**.
3. Workflow получает успешную Windows x64 сборку по номеру run, готовит
   описание версии и пакет. Без deploy пакет сохраняется только в Artifacts.
4. При deploy пакет передаётся на сервер по SSH. Сначала публикуется каталог
   выпуска, затем атомарно переключается описание канала.
5. Клиент проверяет описание через HTTPS, продукт, канал, имя приложения,
   архитектуру, возрастающую ревизию, размер и SHA-256 файла. При отсутствии
   активного сеанса запускается существующий установщик RustDesk `--update`.

SHA-256 проверяет целостность скачанного файла и не является цифровой подписью.
Доверие к обновлению основано на HTTPS и контроле доступа к серверу публикации.
Это наш адаптер собственного адреса обновлений; штатный установщик сохранён.
В оригинальном RustDesk 1.5.0 отдельного управляемого пользователем ключа
подписи обновлений, как в нашей прежней реализации, нет.

## Конструктор

Вставьте в поле «Конфигурация канала обновлений»:

```json
{
  "base_url": "https://desk.status16.ru/client",
  "product": "statusdesk",
  "channel": "test",
  "revision": 1
}
```

Готовый файл: `statusdesk-test.example.json`. В следующей сборке увеличьте
revision до 2. При этом основа RustDesk может оставаться 1.5.0. Продукт, канал
и имя приложения должны сохраняться. Каналы test и stable независимы.
Старые конфигурации с public_key нужно заменить новым примером — они
отклоняются, а не включают другой способ обновления молча.

Первый клиент с адресом канала нужно установить вручную. Затем включите
`allow-auto-update` в клиенте или стратегии CortenDesk. Проверка работает
через установленный Windows-сервис: примерно через 30 секунд после старта,
после успешной проверки — через 24 часа. Если первая проверка не выполнена
из-за сеанса или закончилась ошибкой, повтор — через 30 минут. При последующих
ошибках или занятых сеансах повтор также через 30 минут. Это не немедленная
команда обновления из консоли. Чтобы вернуться к прежнему коду, соберите его с большей ревизией.

## Сервер Apache2

Пользователь уже установил предоставленный файл `desk.status16.ru.conf`.
Путь `/client/` исключён из обычного прокси, WebSocket и подмены названий.
Прежние сертификаты и маршруты CortenDesk сохранены. Изолированный тест
проверяет TLS, точные байты файлов, перенаправление /client, отсутствие
списка каталогов и сохранение прокси-маршрутов. Реальный /login доступен.

Для публикации нужны Python 3.11+ и скрипты `deploy.py`, `release.py`,
`config.py`, `download_catalog.py` в `/srv/stdesk-updates/bin/` (root, без записи пользователю загрузки).
PyNaCl и public-key.hex для канала обновлений больше не нужны.

Для отдельного пользователя stdesk-update без sudo подготовьте каталоги:

```bash
sudo install -d -m 755 /srv/stdesk-updates /srv/stdesk-updates/bin
sudo install -d -o stdesk-update -g stdesk-update -m 755 /srv/stdesk-updates/public
sudo install -d -o stdesk-update -g stdesk-update -m 700 /srv/stdesk-updates/incoming
```

Пользователь stdesk-update и его SSH-доступ ещё требуют настройки.
GitHub Secrets доставки: STDESK_UPDATE_HOST, STDESK_UPDATE_USER,
STDESK_UPDATE_SSH_KEY, STDESK_UPDATE_KNOWN_HOSTS. Это учётные данные доступа
к серверу для загрузки файлов, а не ключи подписи клиента. Личный ключ
администратора сервера использовать для загрузки не следует.

Для ручного переноса можно скачать artifact client-update, передать каталог
bundle любым своим способом и выполнить на сервере:

```bash
python3 /srv/stdesk-updates/bin/deploy.py \
  --bundle /путь/к/bundle \
  --root /srv/stdesk-updates/public
```

Файл канала: /client/channels/statusdesk/test/windows-x64.json.
Пакеты имеют схему 2; прежние подписанные пакеты схемы 1 не поддерживаются.
До изменения схемы ни одного обновления на сервер не публиковалось.

## Ограничения и проверки

Адаптер установленного EXE-клиента поддерживает Windows x64 и x86 / RustDesk 1.5.0 и 1.5.1.
MSI, portable, Linux/macOS и «Только исходящие» пока не подключены.
Нужна практическая проверка обновления между двумя ревизиями в Windows VM,
включая сохранение ID, настроек, входа в аккаунт и локальных псевдонимов.

Локальный зашифрованный файл ключа от прежнего подхода больше не используется.
Он оставлен в исключённой из Git папке; личные резервные копии не удаляются.
Пароли и перенос ключа для дальнейших обновлений не требуются.

Поверхность изменений: отдельный модуль src/rdgen_update.rs, тонкий вызов
из src/updater.rs и отключение прежнего источника в src/common.rs применяются
только при включённом собственном канале. Установка и каталоги настроек
не переписываются. Без конфигурации канала используется прежний исходный код.
Шаблон Apache и CortenDesk при удалении механизма подписи не меняются.


### Независимый канал для базы 1.5.1

При включённом канале отдельный rdgen_update.rs получает metadata только с нашего base_url, сравнивает revision, проверяет продукт/архитектуру, размер и SHA-256. Штатный запрос RustDesk отключён только в этой сборке. Установка запускается существующим Windows EXE-механизмом: адаптер 1.5.1 передаёт ему ожидаемую SHA-256 для дополнительной проверки staging-файла. Собственных ключей подписи нет. Переход 1.5.0.N → 1.5.1.N использует тот же канал и возрастающий номер ревизии. Linux/macOS и MSI не подключены. Без канала исходники updater/common не изменяются.

### Android APK

Публикуется подписанный локально APK из каталога downloads. Перед отправкой проверяются сертификат постоянного Android-ключа, версия и архитектура. Оригинальный stdesk-android-build.json должен находиться рядом с APK. Это обязательная подпись Android-приложения; Windows-канал автообновления не изменяется. Обновления Android устанавливаются вручную поверх прежней версии с тем же пакетом и ключом.


## ZIP для Windows
Публикация Windows EXE дополнительно создаёт ZIP рядом с установщиком и записывает
`zip_url` в downloads.json. Внутри: StatusDesk.exe (x64) либо StatusDesk-x32.exe (x86).
Страница показывает EXE и ZIP рядом. Канал обновлений, имя EXE в манифесте и его
SHA-256 не меняются; автообновление продолжает скачивать EXE.
Для уже опубликованных установщиков запустите на сервере новую версию скрипта:
`sudo python3 download_catalog.py --root /srv/stdesk-updates/public`.
Файл ZIP создаётся до атомарной замены каталога, поэтому кнопка не появится раньше файла.

## Ручная проверка и установка Windows
В новых клиентах с настроенным каналом обновлений слева под ID/паролем
отображается «Проверить обновления» (Windows x64 и x32). Она обращается к службе
StatusDesk и проверяет наш канал той же архитектуры. Если версия новее,
появляется её номер и кнопка «Обновить». Только нажатие «Обновить» запускает
ручное скачивание, проверку метаданных/размера/SHA-256 и штатный установщик.
Ручной запуск не меняет флажок автообновления и работает при его отключении.
Политика запрета установки, MSI и отсутствие установленной службы остаются
ограничениями. Портативный клиент сохраняет штатную кнопку «Установить».
Активные сеансы не прерываются: ручная установка сообщает о необходимости
завершить подключения. После этого можно снова нажать проверку/обновление.
Проверки и скачивания выполняются в службе последовательно; UI опрашивает
только статус. Сам URL/канал или путь установщика через UI не передаются.
Этап «Запускается установка» означает передачу штатному установщику, а не
подтверждение успешного завершения: ошибки запуска остаются в журнале службы.

Изменены только расписание первой проверки в updater.rs, общий модуль
обновления, три локальные команды в существующем IPC/FFI и карточка главного
окна (Flutter либо Sciter). При отсутствии конфигурации канала адаптер ничего
не меняет. Linux/macOS/Android этим механизмом не обновляются.
